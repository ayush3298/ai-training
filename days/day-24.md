## Part G — API & cloud security for an LLM backend

This Part **deepens the backend security [Chapter 8](08-deployment.md) deliberately deferred**. Chapter 8 fixed the *shape* — **client → your backend → provider → back**, with the provider key living server-side only ([Part A](08-deployment.md#part-a--the-shape-of-an-llm-application-in-production)) — and named, but did not build, the next layer: "authenticate *your* users, rate-limit *per user*, don't log secrets" ([Chapter 8](08-deployment.md) Part F). None of this is LLM-specific magic — it's the ordinary web-backend security any API owes — but two pieces take on a sharp LLM twist: a runaway request doesn't just cost CPU, it **spends real provider money**, and a mis-scoped identity doesn't just read the wrong row, it can **leak another tenant's data through retrieval**. So we start from Chapter 8's shape and ask the question it left open: *how do your users authenticate to your backend, and how do you stop one of them from spending everyone's budget?* These controls live mostly at the **INPUT** station (who is this, are they within quota — before the model runs) and the **ACTION** station (is this caller allowed this effect), and they answer **LLM10 (Unbounded Consumption)** and **LLM06 (Excessive Agency)** at the auth layer.

**19. API key vs OAuth2/OIDC is a fork: a key identifies an *application*; OAuth2/OIDC carries a *user*.**
Your backend has to know *who is calling* before it does anything, and there are two fundamentally different answers — this is the fork everything downstream hangs on. An **API key** is a single static secret string that identifies *an application or an account* — "this traffic is from the Acme integration." It's coarse: anyone holding the string *is* that caller, it carries no notion of an individual end-user, and rotating it logs everyone out at once. **OAuth2/OIDC** (OAuth2 is the authorization framework; **OIDC** — OpenID Connect — is the thin identity layer on top that adds *who the user is*) instead issues a short-lived **token** that carries a *specific user's* identity plus **scopes** (the precise permissions that user/token was granted). The difference isn't cosmetic: a key answers *"is this a known app?"* while an OIDC token answers *"which user is this, and what may they do?"* — and only the second can drive **per-user isolation**, because only the second knows there *is* a per-user. This is the identity that feeds [Chapter 4](04-rag.md#part-l--multi-tenant-retrieval--isolation)'s pre-filter: the `tenant_id`/`user_id` you scope retrieval by must come from the *verified token*, never from the request body (a value the caller can set is a value the attacker can set).
- *Analogy:* an API key is the **master key to the building** that the cleaning company holds — it proves *the company* has access, but the door has no idea *which cleaner* walked in, and everyone shares the one key. An OIDC token is each cleaner's **personal badge**: it names the individual and lists exactly which floors their badge opens. You can run a building on a shared master key right up until you need to know who entered which room — and for multi-tenant data, you always need to know.
- *Build consequence:* Use a static **API key** only for *server-to-server* calls where the caller really is one trusted application (and rotate it from the environment, never the repo — [Chapter 8](08-deployment.md) Part A). The moment your backend serves *distinct end-users whose data must not mix*, you need **OAuth2/OIDC** so every request carries a verified user identity, and you derive every isolation scope from that token's claims — not from anything in the request body.

**20. Per-user-token isolation: if A's token can reach B's data, that's the multi-tenant leak at the auth layer.**
[Chapter 4](04-rag.md#part-l--multi-tenant-retrieval--isolation) showed the leak at the *retrieval* layer — post-filtering pulls another tenant's chunk into the candidate pool. **Per-user-token isolation** is the same breach seen *one layer up*, at auth: every data access and every tool call your backend makes on a request must be scoped to the *identity in that request's token*, so that a request authenticated as user A can **never** cause a retrieval or tool call scoped to user B. Concretely: you pull `user_id` (or `tenant_id`) out of the *verified* token's claims and thread it into `retrieve(question, tenant_id=...)` ([Chapter 4](04-rag.md#part-l--multi-tenant-retrieval--isolation)) and into every tool call's authorization check ([Part A](#part-a--a-shared-vocabulary-and-a-map-owasp-llm-top-10--the-four-station-model)'s **ACTION** station). The classic bug — the auth-layer twin of [Chapter 4](04-rag.md#part-l--multi-tenant-retrieval--isolation)'s post-filter leak — is taking the scope from a request *parameter* (`?tenant_id=acme`) instead of the token: now user A simply edits the parameter to `tenant_id=globex` and reads B's data, and your retrieval pre-filter dutifully enforces the *attacker's* chosen scope. The pre-filter was correct; the *scope you fed it* was attacker-controlled. This is **LLM06 (Excessive Agency)** at the identity boundary — the system can act with more reach than the caller is entitled to.
- *Analogy:* a coat-check. You hand over your coat and get a numbered ticket; you can only reclaim the coat your ticket matches. **Per-user isolation is checking the ticket against the coat on every retrieval** — derived from the ticket you were *issued*, not from a coat number you shout across the counter. A cloakroom that hands you whatever coat you *name* is one editable parameter away from giving you someone else's.
- *Build consequence:* Derive every isolation scope (`user_id`/`tenant_id`) from the **verified token**, and write a test that proves a token for user A returns **403/empty** when it tries to reach user B's documents or tools — the auth-layer mirror of [Chapter 4](04-rag.md#part-l--multi-tenant-retrieval--isolation)'s "A can't read B" test. Treat any scope that originates in the request body or query string as attacker-controlled until proven otherwise.

**21. Denial-of-wallet is rate-limiting reframed: the attacker's goal is your provider bill, not your uptime.**
Classic rate limiting protects *capacity* — stop a flood from crashing the box, count requests-per-minute. An LLM backend has a second, nastier exposure that ordinary web rate limiting misses entirely: **denial-of-wallet** (the cost-based reframe of denial-of-service). The attacker isn't trying to take you *down* — a five-figure provider bill is the *win*. They send requests that are individually legal but each maximally expensive: huge inputs, `max_tokens` cranked to the ceiling, the priciest model, in a tight loop. A requests-per-minute limit waves them through, because the abuse isn't in the *request count* — it's in the *tokens and dollars per request*. So the limit you need is a **token/cost budget per user**, not just requests/min: meter each user's consumption in *tokens* (and therefore *dollars*, since cost is tokens × price — [Chapter 8](08-deployment.md) Part C) and **block them past a daily token or dollar cap.** This is **LLM10 (Unbounded Consumption)**, and it lives at the **INPUT** station — you check the caller's budget *before* the expensive provider call, not after the invoice.
- *Analogy:* a corporate fuel card. A requests-per-minute limit caps *how often* you can swipe; it does nothing about *how much fuel per swipe*. The abuser doesn't swipe a thousand times — they swipe once and fill a tanker. The control that actually protects the budget is a **dollar cap on the card**, refilling daily — swipe all you like, you're cut off at the cap. Denial-of-wallet is filling the tanker; a token/cost budget is the cap on the card.
- *Build consequence:* Add a **per-user token/cost budget** (a daily cap in tokens or dollars) and check it at **INPUT** before the provider call; when a user crosses it, refuse with a clear, recoverable error (not a silent 500). Requests/min still has its place against floods, but it is *not* your denial-of-wallet defense — cost abuse hides inside a perfectly modest request rate.

**22. Audit trails: log every consequential action and model call with *who*, so an incident is reconstructable.**
The three controls above *prevent*; an **audit trail** lets you *reconstruct* — and after an incident, reconstruction is the whole game. An audit trail is an append-only log where **every consequential action and every model call** is recorded with **who** did it (the *authenticated user* from the token — concept 19, never a guessed or body-supplied id), **what** (the model, the tool, the action taken), **how much** (tokens/cost — feeding concept 21's budget *and* [Chapter 8](08-deployment.md) Part F's observability), and **when**. The non-negotiable field is *who*: a log that records "an email was sent" is nearly useless during an incident; "user `u_4821` triggered `send_email` to an external recipient at 02:14, 1,900 tokens" is a thread you can pull. And it must obey [Chapter 8](08-deployment.md) Part F's rule — **log the event, never the secret or the raw PII** ([Part B](#part-b--data-governance-what-leaves-your-network-and-on-what-terms)'s redaction applies to your logs too; an audit trail full of un-redacted PHI is itself a breach). This is the on-ramp to [Part I](#part-i--governance-as-engineering-the-threat-model-and-the-operating-loop), where the audit trail becomes a governance and incident-response instrument, not just a debugging aid.
- *Analogy:* a building's entry log paired with its CCTV. When something goes missing, "a door opened at 2am" is noise; "*badge 4821* opened the *vault* door at 2:14am" is an investigation. The identity stamp is what turns a log from a shrug into a lead — and you cannot add it after the fact, so you record *who* on every consequential line from day one.
- *Build consequence:* Emit one structured audit line per request and per consequential action — `{user_id, model, tokens, cost, action, timestamp}` — append-only, with secrets and raw PII redacted. If you can't answer "*which authenticated user* did this, and what did it cost?" from your logs alone, your trail isn't yet auditable, and an incident will be un-reconstructable exactly when reconstruction matters most.

**Hands-on ([Part G](#part-g--api--cloud-security-for-an-llm-backend)):** Extend your [Chapter 8](08-deployment.md) endpoint with the three controls from this Part. (1) **Per-user identity:** add an auth check that resolves a *user id* from the request — stub OAuth2/OIDC or verify a **signed token** (e.g. a symmetric-key JWT, secret from the environment, in Docker) — and reject requests with no valid token (fail-closed). Derive the retrieval/tool scope from that id, **not** from the request body. (2) **Per-user cost budget:** before the provider call, look up the user's tokens-spent-today against a **daily token (or dollar) cap**; if they're over, refuse with a clear recoverable error; after the call, add the request's tokens to their running total. Then **simulate the denial-of-wallet attacker**: drive an abusive loop of expensive requests as one user and **confirm the budget cuts it off** mid-loop (while a second user, under budget, is unaffected — proving the cap is *per-user*, not global). (3) **Audit log:** emit one structured line per request — `{user_id, model, tokens, cost, action, timestamp}`, secrets and raw PII redacted. Report: the cap you set, the request number at which the abuser was blocked, and a sample audit line.

## Part H — Regulation you can act on: GDPR, HIPAA, EU AI Act

Three regimes are most likely to bind an LLM feature, and the temptation is to read them like a lawyer — clauses, recitals, definitions. Resist that. This Part cashes each regime into the **one or two things it makes you BUILD or DECIDE**, and stops there. The rule is **only as much as changes what you ship.** One of the three, **HIPAA**, you already learned in full in [Part C](#part-c--phi--hipaa-when-redaction-becomes-a-legal-standard) — there it was the whole subject; here it is named as *one regime among three* and pointed back to, not re-taught. The other two — **GDPR** (the EU's general data-protection law) and the **EU AI Act** (the EU's law about AI systems specifically) — get their first real treatment here, again only to the depth that lands as an engineering obligation.

A running example carries the whole Part: a **medical-hiring chatbot in the EU** — it screens job applicants for a hospital, reading their resumes and health-disclosure forms to recommend who advances. Hold it in mind, because it is the cleanest proof that these three regimes are *different axes that stack*: the same feature is simultaneously high-risk under the EU AI Act, handling PHI under HIPAA, and processing personal data under GDPR. You do not pick one. You satisfy each.

**23. GDPR's sharpest obligation for an LLM feature is the right to erasure — and the user's data is now scattered across every sink you built.**
**GDPR** (General Data Protection Regulation) is the EU law that governs any processing of *personal data* — any information about an identifiable person — and it binds you the moment an EU resident's data flows through your feature, regardless of where your servers sit. Of its many duties, the one that reshapes your *architecture* is the **right to erasure** (often called "the right to be forgotten"): when a user demands deletion, you must actually delete their personal data — *everywhere it lives.* For a classic web app that means a `DELETE` on a couple of rows. For an LLM feature it is harder, because the same user's data has been **copied into sinks that a `DELETE FROM users` never touches**: it was embedded into your **vector store** ([Chapter 4](04-rag.md)), written verbatim into your **request logs** ([Chapter 8](08-deployment.md)'s per-request logging), and possibly cached in a **semantic cache**. An erasure request that clears the primary database and leaves the vectors, logs, and cache intact has not honored the right — it has *missed three copies*.
- *Analogy:* you spill a cup of coffee, wipe the table, and call it clean — but the coffee already soaked into the napkin, dripped onto the chair, and pooled under the table leg. "Deleted from the database" is wiping the table. Erasure means following every drip.
- *Build consequence:* This is the **same "every copy / every sink" trace** [Part C](#part-c--phi--hipaa-when-redaction-becomes-a-legal-standard) made you run for HIPAA — and that is the point: the discipline is identical, only the legal name on it changes. Before you can claim GDPR compliance, you must be able to enumerate *every place a given user's data comes to rest* (DB, vector index, logs, cache, backups) and have a delete path that fans out to all of them. If you cannot list the sinks, you cannot honor an erasure request. (This is the exact deletion fan-out the Memory chapter makes its climax — the same problem wearing a different hat.) GDPR's fine ceiling is **€20M or 4% of global annual turnover**, whichever is higher — enough that "we forgot about the vector store" is not a survivable answer.

**24. HIPAA is the third axis — already taught, named here only to place it on the map.**
**HIPAA** (the US Health Insurance Portability and Accountability Act) binds any feature that touches **PHI** (Protected Health Information) on behalf of a US healthcare entity, and its core demands — de-identify to the **Safe Harbor** standard before data leaves your boundary, and sign a **BAA** (Business Associate Agreement) with any provider that will see PHI or it is a reportable breach by definition — were the entire subject of [Part C](#part-c--phi--hipaa-when-redaction-becomes-a-legal-standard).
- *Build consequence:* Nothing new to learn — only to *notice* that HIPAA is a **separate axis** from the other two, not a substitute. The medical-hiring chatbot reads applicants' health-disclosure forms, so it handles PHI; that obligation (redact to Safe Harbor, sign the BAA) stands *on top of* whatever GDPR and the AI Act ask, not instead of it. Re-run [Part C](#part-c--phi--hipaa-when-redaction-becomes-a-legal-standard)'s every-sink trace for PHI specifically; satisfying GDPR erasure does not automatically satisfy HIPAA de-identification, and vice versa.

**25. The EU AI Act sorts your feature into a risk tier — and the tier you land in is a decision YOU make about your own build.**
The **EU AI Act** is the first broad law that regulates AI *systems* by what they are used for, and the beginner's mistake is to assume it is "a law for the people who train models." It is not — it binds **deployers and providers of AI systems**, which includes you, the engineer wiring an API into a product. The Act works as a **risk-tier ladder**, and your job is to decide which rung *your own feature* sits on:
- **Prohibited** — uses banned outright (social scoring, certain biometric surveillance). You do not build these.
- **High-risk** — systems used for consequential decisions about people: **employment** (hiring, firing), **credit** and essential services, **medical** decisions, education, law enforcement. These carry the heavy obligations — risk management, logging, human oversight, conformity assessment.
- **Limited risk (transparency)** — systems that interact with people or generate content but don't make high-stakes decisions. **This is where most features built on an API land.**
- **Minimal risk** — everything else (a spam filter, a game NPC); essentially no obligations.

Most API-built features sit in **limited risk**, and the duty that tier imposes is **Article 50 transparency**: you must **disclose that the user is interacting with an AI system** (not a human), and **label AI-generated content** as artificial. That is the whole obligation for the common case — a one-line disclosure, not a compliance department. You climb *up* the ladder only when your feature hits a **high-risk trigger** — and the triggers are exactly the consequential-decision domains above: **employment, credit, medical decisions**. The medical-hiring chatbot trips *two* triggers at once (employment *and* medical), so it is unambiguously high-risk.
- *Analogy:* the risk tier is a **building occupancy classification**, the kind a fire marshal assigns. A storage shed and a hospital follow wildly different codes — sprinklers, exits, inspections — not because the *walls* differ but because of **what happens inside**. You read your own blueprint, find the use, and that tells you which code book applies. A chatbot that recommends lunch and one that screens job applicants are the same *technology* in different occupancy classes.
- *Build consequence:* Before you ship, **classify your own feature against the ladder** and write the tier down with its justification — this is a decision you own, and it is the first line of the regulatory determination in this Part's Hands-on. If you land in limited risk, the build change is small and concrete: add the **AI-interaction disclosure** to your UI and/or system prompt, and label generated content. If a high-risk trigger fires, the obligations are heavy enough that "are we in scope?" becomes a go/no-go gate on the whole product. Enforcement of the high-risk obligations begins **2026-08-02**, and the fine ceiling is **€35M or 7% of global turnover** — the steepest of the three regimes, which is why mis-classifying *upward-by-accident* (calling a lunch bot high-risk) wastes money and mis-classifying *downward* (shipping a hiring bot as "limited risk") can halt the product.

**The three regimes stack — they are axes, not a menu.** The single confusion to kill before leaving this Part: these do **not** compete, and satisfying one says nothing about the others. The medical-hiring chatbot is **high-risk under the EU AI Act** (employment + medical triggers) **AND** processing **PHI under HIPAA** (it reads health forms) **AND** processing **personal data under GDPR** (the applicants are people, some in the EU) — *all at once.* Three different questions, three independent obligations: the AI Act asks *"how consequential is the decision?"*, HIPAA asks *"is this health data, and did you sign the BAA?"*, GDPR asks *"can you find and delete this person everywhere?"* You answer each on its own axis. A feature can be limited-risk under the AI Act yet still owe a full GDPR erasure path; it can be GDPR-clean yet a HIPAA breach for want of a BAA.

**Hands-on ([Part H](#part-h--regulation-you-can-act-on-gdpr-hipaa-eu-ai-act)):** For the feature you've carried through this chapter (your [Chapter 4](04-rag.md) RAG bot or [Chapter 5](05-agents.md) agent), write a one-paragraph **regulatory determination** on all three axes. (1) **EU AI Act tier:** state the tier (almost certainly *limited risk* unless your feature touches employment, credit, or medical decisions) and name the trigger — or name its *absence* ("no high-risk trigger: it answers product questions, makes no consequential decision about a person"). (2) **GDPR:** state whether it applies (does any EU resident's personal data flow through it?), and if so **list every sink where that user's data comes to rest** so an erasure request could actually be honored — at minimum: primary DB, **vector store**, **request logs**, **semantic cache**, backups. If you cannot enumerate the sinks, that gap *is* the finding. (3) **HIPAA:** state whether it applies (any PHI?) — for most non-health features, "no," with one sentence why. Finally, **if a transparency duty applies** (limited risk under the AI Act), write the literal **AI-disclosure line** and say where it goes — a banner in the UI, a line in the system prompt, or both (e.g. *"You're chatting with an automated assistant, not a human agent."*).

## Part I — Governance as engineering: the threat model and the operating loop

Here is the reframe that makes governance bearable: it is **not paperwork bolted onto a finished feature.** It is the **engineering discipline this course already taught you** — versioning, eval gates, audit logs, incident response — pointed at *security* instead of quality, and held together by **one written artifact: a threat model**. You are not learning four new practices in this Part. You are re-aiming four you already own, and then tying them to a one-page document that makes the whole chapter's map concrete. By the end, the **four-station map from [Part A](#part-a--a-shared-vocabulary-and-a-map-owasp-llm-top-10--the-four-station-model)** is filled in for your feature — the chapter ends exactly where it began.

A **threat model**, defined plainly at first use, is a short written document that answers four questions about a feature: what are you protecting (**assets**), who would attack it (**adversaries**), how could they (**attack paths**), and what stops them where (**controls**). It is the security cousin of the design doc — and like a design doc, its value is that it exists *on paper before the incident*, not in someone's head after one.

**26. Three governance practices you already own, re-aimed at security: versioning + eval gates, audit logs, incident response.**
Walk the three, each mapped to a concept you can already build:
- **Versioning + eval gates → now a *security* gate.** You already version prompts and gate deploys on an eval score ([Chapter 7](07-evaluation.md) Part D/I; [Chapter 8](08-deployment.md)'s rollout ladder). A **security eval gate** is the same machinery with security test cases added: a prompt change that quietly *weakens an injection defense* must **fail a gate** exactly the way a change that drops accuracy does. The injection probe from [Chapter 4](04-rag.md) that your feature is supposed to refuse becomes a permanent regression case — if a "harmless" prompt edit makes the model start obeying it, the gate goes red and the deploy is blocked. Security regressions get caught by the *same gate* as quality regressions; you just have to put the security cases in it.
- **Audit logs → who-did-what + every request.** You already log every request ([Chapter 8](08-deployment.md) concept 16: input, assembled prompt, response, tokens, model) and, from [Part G](#part-g--api--cloud-security-for-an-llm-backend), the *who-did-what* trail of which user/key took which action. Together that *is* your audit log: when something goes wrong, it answers "what did we tell this user, what did the system do, and on whose authority" — without it, an investigation is guesswork.
- **Incident response → a security playbook on the monitor→alert→investigate loop.** [Chapter 8](08-deployment.md) concept 18 gave you the operating loop: **monitor → alert → investigate via logs → fix → add to eval → redeploy.** A **security incident-response playbook** is that same loop with security-specific triggers and runbooks written *in advance*: what do we do the moment a **key leaks** (rotate it, audit its usage from the logs), a **data leak** is detected (scope it from the audit trail, notify per the breach rules in [Part H](#part-h--regulation-you-can-act-on-gdpr-hipaa-eu-ai-act)), or an **injection succeeds** (pull the trace, add the payload to the security gate so it can't recur)?
- *Analogy:* governance is not a new building inspector who shows up after the house is built. It is the **electrician, plumber, and fire-alarm tech you already hired** — the same trades, now asked to wire the *security* circuit too. You are not staffing a new department; you are giving the existing crew the security blueprint.
- *Build consequence:* Do not stand up a parallel "governance system." Extend what runs: add security cases to the eval gate, make sure the request log captures the who-did-what, and write the three short runbooks (key leak / data leak / successful injection) *before* you need them. Governance lands as commits to systems you already operate, not as a new tool.

**27. The keystone is a one-page threat model — and it is literally the Part A four-station map, completed.**
Everything above hangs on one artifact. A **threat model** for an LLM feature is a one-page document answering four questions — and the fourth answer *is* the chapter's spine:
- **Assets** — what are you protecting? The concrete list: **API keys / secrets**, **PII/PHI**, **tenant data** (another customer's rows), and — unique to LLM features — **the action capability itself** (the tools the agent can invoke; the ability to *send the email* or *write the row* is an asset because it is what an attacker wants to seize).
- **Adversaries** — who attacks? Name them: the **malicious user** typing an override into the box, the **poisoned document** your own retriever pulls ([Chapter 4](04-rag.md) — the adversary is the *content*, not a person at a keyboard), and the **compromised provider or dependency** (a supply-chain risk — the model, library, or MCP server you trusted).
- **Attack paths — mapped to OWASP ids from [Part A](#part-a--a-shared-vocabulary-and-a-map-owasp-llm-top-10--the-four-station-model).** For each adversary, the route to an asset, named by its OWASP code so you and a reviewer share the word: direct or indirect **prompt injection (LLM01)** reaching the action capability; **sensitive-information disclosure (LLM02)** leaking PII into output; **system-prompt leakage (LLM07)** exposing what's hidden in the prompt; **excessive agency (LLM06)** letting the model do more than it should; **cross-tenant vector leakage (LLM08)**; **denial-of-wallet (LLM10)**.
- **Control at each of the four stations** — and *this is [Part A](#part-a--a-shared-vocabulary-and-a-map-owasp-llm-top-10--the-four-station-model)'s diagram, filled in.* For each attack path, what control sits at **INPUT** (classifier, redaction), **MODEL** (instruction hierarchy, least-privilege, the provider contract from [Part B/G]), **OUTPUT** (leak-scan, schema validation, de-anonymize — the ordered [Part E] guardrail), and **ACTION** (tool allowlist, argument validation, per-user authorization, human-in-the-loop for irreversible effects). Pull the guardrail bill-of-materials straight from [Part F](#part-f--which-guardrail-a-build-vs-buy-menu-mapped-to-stations) (risk → station → tool) and the injection architecture from [Part D](#part-d--prompt-injection-in-depth-climbing-to-architectural-defenses).
- *Analogy:* the threat model is the **fire-escape plan posted on the back of a hotel door** — assets are the people in the rooms, adversaries are the ways a fire starts, attack paths are how smoke travels, and the controls are the marked exits and extinguishers. It is one page, it is on the wall *before* the alarm, and in the emergency nobody has time to invent it. The map from [Part A](#part-a--a-shared-vocabulary-and-a-map-owasp-llm-top-10--the-four-station-model) was the blank version of this poster; the threat model is it filled in.
- *Build consequence:* This one page **is the chapter's deliverable.** A security review of your feature is not a vibe or a checklist sweep — it is, literally, *writing these four answers down*, with the fourth being the four-station map completed for your feature. If a station has an attack path reaching it and no named control, that empty cell is the finding the review exists to surface. The chapter that opened by drawing four empty checkpoints ends by handing you those four checkpoints filled in for something you actually built.

**28. Governance is continuous: re-review the threat model whenever the feature gains a new capability.**
A threat model is not a document you write once and file. **Every new capability opens a new attack path**, so the threat model must be re-reviewed whenever the feature *gains* one — a **new tool** the agent can call, a **new data source** the retriever pulls, a **new integration** with another service. Add a tool that can issue refunds, and you have added an asset (the refund capability) and an attack path (injection → unauthorized refund) that your last threat model never considered; the ACTION-station control that was complete yesterday now has a hole.
- *Analogy:* it is the **eval flywheel** ([Chapter 7](07-evaluation.md) concept 27) wearing security clothes — production keeps revealing new cases, and the eval set is never "done." Likewise the attack surface keeps growing as the feature grows, and the threat model is never "done." Both are loops, not milestones.
- *Build consequence:* Make "re-review the threat model" a **required step in the change process for any new capability** — gate it the way you gate a deploy. Concretely: when a pull request adds a tool or a data source, the threat model gets a diff in the *same* PR, and the new attack path gets a control (and a security gate case) before it merges. Governance is the operating loop, run forever — monitor the feature, and every time it grows, walk the new capability back through assets → adversaries → paths → controls. The map is alive because the feature is.

**Hands-on ([Part I](#part-i--governance-as-engineering-the-threat-model-and-the-operating-loop)):** Write the **one-page threat model** for your feature — this is the chapter deliverable. (1) **Assets:** list them — API keys, any PII/PHI, tenant data, and your feature's specific **action capability** (name the tools it can call; if it's pure RAG with no tools, say so and note the action surface is "retrieval only"). (2) **Adversaries:** name the malicious user, the poisoned retrieved document, and the compromised provider/dependency relevant to *your* feature. (3) **Attack paths as OWASP ids:** for each adversary, the route to an asset tagged with its [Part A](#part-a--a-shared-vocabulary-and-a-map-owasp-llm-top-10--the-four-station-model) code (e.g. *poisoned doc → LLM01 indirect injection → LLM06 excessive agency → `send_email` to attacker*). (4) **Control at each of the four stations:** complete the [Part A](#part-a--a-shared-vocabulary-and-a-map-owasp-llm-top-10--the-four-station-model) map — INPUT / MODEL / OUTPUT / ACTION — for each path, pulling the **guardrail bill-of-materials from [Part F](#part-f--which-guardrail-a-build-vs-buy-menu-mapped-to-stations)** and the **injection architecture from [Part D](#part-d--prompt-injection-in-depth-climbing-to-architectural-defenses)**; an empty cell with a live attack path reaching it is a finding to fix. Then (5) **add one security regression test to your eval gate** — e.g. *the [Chapter 4](04-rag.md) injection probe must still be refused* — so a future prompt edit that weakens the defense turns the gate red. Finally (6) **state the one capability change that would force a threat-model re-review** — the next tool or data source you'd add (e.g. *"adding a `send_email` tool would open an exfiltration path and require re-reviewing the ACTION station"*).

**Answer key** — *peek only after attempting.*

1. Redaction — *you send less* — at INPUT; and the provider contract (ZDR/DPA/residency) — *they promise less* — at MODEL. They're orthogonal (different targets) and stack as defense in depth.
2. Every provider has a *default* retention policy (a retention window, sometimes training-on-data unless opted out), so signing/toggling nothing silently selects provider-default — the least private tier.
3. Because instructions and data share one token stream with no enforced escape; the labelling and ranking are behavior the model is trained to *prefer*, not a wall it *cannot* cross — so they lower the probability of a hijack, never eliminate it.
4. Leak/PII scan, content-safety moderation, grounding/faithfulness check (RAG), and de-anonymization — and the rule is: scan for unexpected PII *before* restoring your intended tokens (full order: validate → scan → moderate → ground → de-anonymize).
5. **risk → station → tool**: start from a *named failure* (an OWASP LLM code), let it point you to the *station* on the four-station map, and let the station narrow the catalogue to the right *kind* of tool. Never start from the tool.
6. It's the cost-based reframe of denial-of-service: the attacker's goal is to run up your provider bill, not to crash you. A requests/min limit only counts *how often* you're called; the abuse hides in *tokens/dollars per request* (huge inputs, max `max_tokens`, priciest model), so a modest request rate sails through. The fix is a per-user **token/cost budget** checked at INPUT before the call.
7. An API key is a static secret that identifies an *application/account* (coarse, no individual user). An OAuth2/OIDC token is short-lived and carries a *specific user's* identity plus scopes. Only the token knows there *is* a per-user, so only it can drive per-user isolation — and the isolation scope must come from the verified token, never the request body.
8. Limited risk. The obligation is Article 50 transparency: disclose that the user is interacting with an AI system and label AI-generated content — in practice, a one-line disclosure in the UI and/or system prompt.
9. The vector store (embedded chunks), the request logs (verbatim inputs), and the semantic cache. (Backups also count.) Erasure must fan out to all of them or it isn't honored.
10. Reversible tokenization: send a stable token (<PERSON_1>) and keep an in-memory restore map {token→original} that never leaves your infra; swap originals back into the response. The restore map must stay local.
11. Yes — a breach by definition. Once real (not-yet-de-identified) PHI reaches a provider, HIPAA requires a signed BAA; without it the send itself is the violation. Fix: de-identify before the boundary, or use a BAA-covered endpoint.
12. Move from classifier-plus-labelling to an *architectural* split (dual-LLM/CaMeL): once the model can take a consequential, irreversible action, a missed injection is a breach not a bad answer, so you must remove the model's authority to act on untrusted text rather than just lower the odds of being fooled.
13. The PII scanner now flags your own restored values (e.g. the legitimate `Jane Doe`) as leaks, and it can no longer distinguish your intended restorations from a real name the model leaked — you get false alarms and weakened detection of the actual breach. Scan on tokenized text first; restore last.
14. **Presidio — INPUT — LLM02** (redact emails/PII before the provider call; self-hosted so personal data never leaves). **Llama Guard self-hosted — INPUT — LLM01** (jailbreak/content screen kept in-network, chosen over Bedrock Guardrails precisely because you won't send user text out to a managed scanner). No orchestrator — only two rails, so rung 3 isn't justified.
15. The pre-filter is correct but the *scope you feed it* is attacker-controlled: user A edits the parameter to another tenant's id and the pre-filter dutifully enforces the *attacker's* chosen scope (LLM06 at the auth layer). Fix: derive `tenant_id`/`user_id` from the **verified token's claims**, never from the request body/query, and test that A's token gets 403/empty for B's data.
16. EU AI Act: how consequential is the decision? (high-risk — employment + medical triggers). HIPAA: is this health data, and did you sign a BAA? (yes — it reads health forms). GDPR: can you find and delete this person across every sink? They are independent axes; satisfying one says nothing about the others.
17. Add security test cases to the same gate: e.g. the Chapter 4 injection probe must still be refused. A prompt change that weakens the injection defense then fails the gate exactly like a change that drops accuracy — security regressions caught by the same machinery.
18. Wrong default: Safe Harbor is a codeable 18-item checklist (a unit test) with no expert needed — cheaper and auditable. Expert Determination is right only when Safe Harbor strips a field the feature genuinely needs (e.g., admission dates or ZIP-level data); it costs a statistician, a written sign-off, and re-review.
19. De-identification is a property of *every copy*, not the model call. The raw name can still sit in the vector store, request logs, and cache. Rule: trace PHI to every sink and redact upstream of all of them — prompt, vector store, logs, cache.
20. Because CaMeL fixes the planner's *control flow* before the data arrives: untrusted content can only fill *values*, never choose *which steps run*. The planner treats `action_item` as a string to display, not a command to execute, and it never had `send_email` authority wired to that field — so the line is inert data, not a branch.
21. It pattern-matches known attack shapes at the INPUT station, so it has a structural false-negative rate against novel phrasings/encodings; its right role is cheap volume-reduction *in front of* the real defense — for action-capable features the backstop must be the ACTION-station architecture (authority removed), because the classifier only changes how often you're attacked, not whether a missed attack can land.
22. A monolith gives you a heavyweight dependency, a new config language, and a roadmap you don't control — and still defends *generic* stations, not the one place *your* feature leaks. Instead, **compose small tools at stations with named, unguarded failures**; an empty station is a station with no failure yet named, and a control with no failure to catch is pure cost (latency, money, false positives) for zero risk reduction. Buy a tool only for a station with a named failure.
23. It's missing **who**: without the *authenticated user id* from the token, you can't pull the thread during an incident. Add `user_id` (from the verified token, never a body-supplied value) to every consequential line. Caveat: the trail must still obey "log the event, never the secret or raw PII" — an audit log full of un-redacted PHI is itself a breach, so Part B redaction applies to logs too.
24. The four stations (INPUT→MODEL→OUTPUT→ACTION) are Part A's blank diagram; filling in a control for each attack path at each station IS that diagram completed for your feature — the chapter ends where it began. You redo it whenever the feature gains a new capability (a new tool or data source), because each new capability opens a new attack path — governance is a continuous loop, like the eval flywheel.
25. Redacting the input doesn't address erasure at all — and raw personal data may still be sitting in the vector store, request logs, cache, and backups. GDPR erasure requires enumerating every sink where a given user's data comes to rest and having a delete path that fans out to all of them; input redaction is a different control answering a different obligation.
